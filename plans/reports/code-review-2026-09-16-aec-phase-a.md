## Findings

### High

**H1 — `SpatialIndex` silently drops an oversized item from all but its first 64×64 cells → missed pairs and missed spatial matches**
`HPAutoCad/HPAutoCad.Aec/Spatial/SpatialIndex.cs:69-73`. When a box spans > 4096 cells the loop clamps `x1 = x0 + 63; y1 = y0 + 63`, so the item is only registered in the bottom-left corner of its extent. Cell size = 2 × median item size (`:62`), so in any drawing where small entities dominate (text, symbols, short wall lines → cell 0.4–4 m) every outline/frame/site boundary larger than ~64 cells on both axes is truncated. Probe (200 boxes of 200 mm + one 30 m ring, cell 400): `Query` at the far corner does not return the ring. Consequences: (1) `query_entities_spatial` `within/contains/intersects/…` misses the big target for every source outside that corner (`SpatialQueryService.cs:43,61`); (2) `GeometryIssueDetector.PairwiseChecks` (`GeometryIssueDetector.cs:104-106`) only checks a pair when `Query(a)` returns `b` with `j > i` — probe: `overlapping_segments` between a line and the ring is found when the ring is inserted first and **missed when it is inserted after** (drawing order = insertion order, so results depend on creation order). Fix: keep oversized items in a separate `_oversized` list that `Query` always tests with `Bounds.IntersectsXY(expanded)` (three lines), or rebuild with a larger cell when any item exceeds the cap. Add a test: many small + one huge, query far corner.

**H2 — `Arc` entities are tessellated in the OCS as if the normal were +Z; mirrored arcs come out mirrored**
`HPAutoCad/HPAutoCad.Aec/Cad/EntityShapeReader.cs:122-125`. `Arc.StartAngle/EndAngle` are measured in the entity's OCS; `Arc.Center` is WCS. For `Normal = (0,0,-1)` (every arc produced by MIRROR, common for door swings) the OCS X axis is WCS −X, so `ArcPoints(center, r, startAngle, sweep)` produces the reflection of the real arc about the vertical through the centre: wrong endpoints (→ false `endpoint_gap`), wrong crossings/containment, wrong `closestPoint` fallback. `Circle` (`:118-121`) is only orientation-flipped (harmless). The polyline path is correct because `GetArcSegmentAt` returns a WCS `CircularArc3d`. Fix: sample through `arc.GetGeCurve()` exactly as `SampleCurve` does (`Helpers.cs:14-34`), or transform with `Matrix3d.PlaneToWorld(arc.Normal)`; keep `Mm(arc.Length)` as the exact length. Add a harness scene arc with `Normal = -Vector3d.ZAxis` and assert `measure_geometry closestPoint` / `detect_geometry_issues endpoint_gap` against its `StartPoint`.

**H3 — Default limits breach the bridge's 64 KB output cap; the AI then receives truncated text instead of JSON**
`HPAutoCad.Mcp.Server/Registry/SeedLibrary/Audit/detect_geometry_issues/tool.json:162` (`"default": 200`) and `HPAutoCad/HPAutoCad.Aec/AecTools.cs:22` (`DefaultLimit = 100` also for `mode: detail`), `Model/AecEntityRecord.cs:59-62` (`ToGeometry` emits every tessellated vertex). Measured with realistic handles/layer names: one issue = 330–352 B → 200 issues ≈ 70 KB; one detail record with a tessellated circle (141 vertices at the default chord error) ≈ 5.2 KB, a 10 m circle ≈ 13 KB, a spline up to 15 KB → 12 items fill the cap. Over the cap `AutocadResultSerializer` returns the head as a string (`:57-59`), so `success/count/truncated` are lost. Fix: issues default `limit` 100 (150 max safe); in detail mode cap `geometry.vertices` (e.g. 64, with `verticesTruncated: true` and the count) or lower the detail default to 20; add a size guard test that serialises a worst-case page with `BridgeJson.Options` and asserts `< 60 KB`.

### Medium

**M1 — Predicate semantics are not mutually consistent for near-collinear and edge-sharing geometry**
`Geometry/GeometryMath.cs:33` treats "parallel" as `|r × q| ≤ 1e-12` (absolute, in mm²) — effectively bit-exact. Two lines drawn on top of each other from different sources (`(0,0)-(1000,0)` vs `(500,0.001)-(1500,0.0011)`) take the non-parallel branch, `v` falls outside the slack and `IntersectXY` returns `None`, so `intersects = false` while `overlaps = true` and `touches = true` (probe). Also `touches` (`SpatialPredicates.cs:48-55`) does not exclude collinear overlap, so two overlapping wall lines and two adjacent rooms sharing an edge are both "touches" and "overlaps" (`:56-68`). Suggest: parallel test relative to `tol.ParallelAngle` (`|r×q| ≤ sin(angleTol)·|r|·|q|`), then the collinear branch applies its distance tolerance; `touches` = `distance ≤ EndpointConnection && !proper && !contained && CollinearOverlaps().Count == 0`; document (tool description) that `overlaps` on rings includes shared edges, or split into `shares_edge`.

**M2 — `tiny_segment`/`zero_length`/`overlapping_segments` fire on tessellation chords and bounding-box rectangles**
`Issues/GeometryIssueDetector.cs:60-71, 137-143`; shapes from `EntityShapeReader.cs:118-125` (circles/arcs) and `:136,141,146,151,160` (INSERT/TEXT/MTEXT/DIMENSION/other as bbox rectangles). Chord length at the default chord error is ≈ √(2r) mm, so every circle/arc with r ≤ 12.5 mm (bolt holes, fillets, rebar bends) reports up to 5 `tiny_segment` issues (probe: r = 10 mm circle → 5 issues). A block/text bbox edge lying on a wall/grid line produces `overlapping_segments LINE × INSERT`; a flat block reports `zero_length`. Fix: give `PlanShape` a `Source` (`Exact | Tessellated | BoundingBox`) or `IsApproximate` flag set by the reader; skip the single-shape segment checks for tessellated/bbox shapes and `overlapping_segments` when either side is a bbox.

**M3 — Unbounded cell walks and full pairwise `nearest`**
`Spatial/SpatialIndex.cs:38-50` iterates every cell in the query range: with a small cell (many tiny items) a large query box or a large `maxDistance` costs millions of dictionary lookups per source (probe: 100 items, cell 20, one 200 km query → 2.4 s). `SpatialQueryService.cs:61` uses `index.All()` for `nearest` without `maxDistance` → O(sources × targets) with per-pair segment maths (fine for the 1000×1000 lines in the harness, not for polylines/circles). Fix: in `Query`, if `(cells in range) > _items.Count` scan `_items` linearly; for `nearest` without a radius, search expanding rings around the source cell and stop once the ring distance exceeds the best distance.

**M4 — Dynamic block instances are invisible to `blockNames` filters**
`Cad/EntityQueryService.cs:103` (`DxfCode.BlockName` sees the anonymous `*U12` name) and `:148` (`block.Name` on the handle path), while the record's `blockName` reports the dynamic block's original name (`EntityShapeReader.Helpers.cs:50-61`). A user filtering `blockNames: ["DOOR*"]` gets zero dynamic doors although `query_entities` labels them `DOOR`. Fix: when `BlockNames` is set, drop it from the `SelectionFilter` (keep type INSERT) and post-filter on `BlockName(block)`; or include `*U*` in the selection and post-filter.

**M5 — `measure_geometry distance` hides the real cause when a handle fails**
`Cad/MeasureService.cs:141-160`: with two handles where one is invalid, `entities.Count == 1` and `pointsMm` empty → `throw new ArgumentException("distance needs two points, two handles, or one handle and one point.")` while `result.Errors` already holds the `INVALID_HANDLE`/`ERASED` entry that is then discarded. Same pattern for `intersections` (`:176`). Fix: if `result.Errors.Count > 0` return the envelope with `Success = false` (or include the codes in the exception message).

## Positive observations

- Clean split: `Geometry/Spatial/Issues/Model` never touch an AutoCAD type and are covered by 45 focused tests; adapters are thin and every AutoCAD call that can throw is contained per entity (`GeometryNote` instead of a failed run).
- Seeds are genuinely data + a shim (`SeedLibraryTests.Aec_seed_is_a_thin_shim_over_the_engine` pins ≤ 12 lines, one `AecTools.` call, `transaction none`, "Read-only" in the description); the bridge/test compile references mirror each other exactly.
- Units contract honoured end to end (`Mm()` at every boundary, areas × `MmPerUnit²`, verified live on an imperial template).
- Exact AutoCAD maths where it matters (`GetDistanceAtParameter`, `Curve.Area`, `GetClosestPointTo`, `IntersectWith`) with the tessellated engine as a documented fallback.
- Handle resolution is typed (`INVALID_HANDLE`/`ERASED`/`NOT_AN_ENTITY`) and never leaks `ObjectId`; paging keeps counting after the page so `count` is exact; `maxCandidates` + `truncated` avoid silent full-drawing walks.
- `ScriptingSelfCheck` now proves the Aec assembly resolves in the bridge's load context, and the harness greps the log line for it.

## Score and verdict

**7 / 10.** The engine is well-structured, tested and read-only by construction, and the five tools work live. Three defects should be fixed before this lands because they invalidate results silently: the spatial index truncation (H1 — order-dependent misses in two tools), mirrored arcs (H2 — wrong geometry for a common entity), and the default page sizes that exceed the 64 KB serializer cap (H3 — the AI gets a string, not JSON). All three are small, local changes with an obvious unit test each; M1–M5 can follow in a phase-A.1 tidy-up before phase B builds classification on top of the same predicates.

**Verdict:** DONE_WITH_CONCERNS — fix H1, H2, H3 (and re-run `HPAutoCad.Aec.Tests` + `run-aec-tools-live.ps1`) before commit; M1/M2 before phase B relies on `touches`/`overlaps` and on the issue detector.
