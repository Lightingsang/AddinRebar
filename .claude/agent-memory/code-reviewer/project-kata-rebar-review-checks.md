Checks that found real defects in the Kata rebar core (2026-10-02 layer-spacer-tie review):

- Asymmetric "left;right" support cells produce two sub-rows (`…T`/`…P`) with the SAME `HostSupportIndex` + `Layer`; anything grouping by those keys merges two cross-sections (bar-count thresholds and "outer bars" go wrong).
- `KataTieWrap` offsets a wrapping tie by the tie's bend radius only — fine for side bars Ø12–16, clashes with wrapped bars ≥ Ø22. DY7 golden sheet uses Ø18 so tests never see it.
- Sheet spacing cells (J7 etc.) parsed with "any v > 0" — probe a typo like `a5`: thousands of bars, no warning.
- LikeHoops-style "+2Ø along X" shifts point outward at a RIGHT cantilever tip.
- Bottom row 17 is `Layer == 2` even when it is seated on the stirrup (no level beneath).

- Section n-n drawing (`KataSectionDrawingBuilder`, 2026-10-03): tag rows are fixed offsets fitted to 2-layer DY7/DY14 samples. 3+ top layers (C15/E15/G15 = "2f18") stack inner-layer tags 43 mm apart at one insertion; ≥ 2 bottom middle numbers (D18 = "2f20+2f22") put a row 31 mm above the width dim (dimZ allows one extra row only). Base DY7 already has side-bar vs inner tag 119 mm apart — that is Kata's own, not a bug.
- Canvas section cache keyed by cut Number is sound: `KataSectionCuts.Content` covers everything the builder reads.

- Canvas bar-group removal (`KataLayoutRemoval`, 2026-10-04): `KataStirrupRuns.Of` merges same-span/number/spacing zones without a contiguity check, so striking a mid-span zone fuses both dense zones into one a100 run (lines, dims, tags, selection). Removal never touches `BarSets` (side ties, layer-spacer ties, inner stirrups) — striking everything still leaves 58 bars / 10 kg on DY7. Keys use the ordinal `BarId`: one extra bar earlier in the order makes 11/28 old keys name a different bar, and the `unknown` check cannot see it.

- Kata Export row 20 (2026-10-04): at a span, the token `0` means "no side bars" (the project's own `KataBarNotationParser.ParseBarList` treats it that way), so any "drop plain-number tokens = old width" merge must keep `0`. Crossing beams come only from probes along the run centre line through the crossing beam's uncut solid. A beam framing into a column from one side ends at the column centre, so an edge beam set flush with the column's outer face never meets it. Kata carries empty row 20/21 span cells from the previous span (the B01 live test showed this for side bars), so check whether a span that goes back to B6 width must be written explicitly.

- Top drops / span widths (2026-10-05, `KataTopProfile`/`KataWidthProfile`): layout z = 0 is the LEVEL datum (row 19 = Revit top − level), but `KataBeamPlacement` puts z = 0 at `run.Pieces[0].TopFt` (Revit-first piece's real top) — any run whose first piece has a z offset is shifted. `KataWidthProfile.Cut` drops the whole side shorter than 2·G3·d (short span / narrow console loses its main bars). Revit-measured tops are raw doubles and transitions use 1e-6, `Cranks` needs Ø ≥ 16 → a 0.4 mm top mismatch cuts every Ø14 top bar. Station crank always runs into the next span (wrong for a downward step). Width + top cut at one support duplicates a stub. B5 is the reference soffit (first span row 21 may be ≠ 0); comparing it to the measured soffit depth warns/blocks spuriously. Split hoop zones share `ZoneName` (removal of inner stirrups) and single-bar fallback takes the span's first zone number.

- Consoles + row 19/21 span bars (2026-10-05, `KataMainBarSwap`, `ConsoleRun`): two independent "cut at a support" paths (bottom-run planner / `KataTopProfile` vs `KataWidthProfile` bar-or-width change) meeting at one support leave duplicate hooked stubs — probe console + width change, console + own row 21 bars, top step + own row 19 bars. Lap/anchorage are sized before the swap (B11/B12 Ø), so larger span bars are under-lapped; B01 DWG bottom laps are 30×Ø20 from the support FACE (24400, 31800), tests use ±200 / skip it. `KataBarItem` record equality includes `RawNotation` ("6F25" ≠ "6f25"). Planner runs `Calculate` even when scope blocks → a blocked sheet can throw instead of listing blocks. Probe a console of h 280 (10d leg above the top), n = 1 console, equal-depth console (coincident lap bars), both-end consoles over columns.

- Support-cell reporting (2026-10-05, joint cells): "zero width" is decided twice — parser `width > 0` vs `KataZeroWidthSupports.IsZeroWidth` (excludes `WidthUnreadable`) — so cells at an unreadable-width support (`abc`, `0.0`) fall through both. `Note()` skips only empty, `ReportCells` also "0"/"-" → noise notes. Bars injected into a joined span flip layout rules keyed on "row 17 filled" (own row 18 extended by G1). Span-rule cuts (≤ L/6) do not cover a joint near an end. Notes with an Outcome still go to `Skipped` ("[Bỏ qua]").

- Loads on a span (2026-10-05, `KataJointStirrups`/`KataHangerBarLayout`, spec loads injected via `spans[i] with { Loads = … }`): hanger path never clipped to span/beam ends (load 350 from C → bar at x −533; console tip overrun); 2 top bars → both hangers at y 0; neighbouring loads ≤ ~700 apart → coincident joint hoops + duplicate zone keys; `Cut` → 10 mm pairs / 2.6× gaps (scan load position in 10 mm steps, print min/max hoop gap); hangers in `LongitudinalBars` show in sections as bottom bars but the elevation canvas never draws them; `ZoneIndexOf` default 0 for "[k]" parts and joint zones.

- B01 parity + Revit numbering (2026-10-05, `KataRebarNumberAssigner`/`KataRebarStorage`): `NumberingSchema.ChangeNumber` moves EVERY element with that number in the partition (foreign/hand bars too; empty beam name = Revit default partition shared model-wide); it throws Revit `ArgumentException` (to exists / from absent), `InvalidOperationException` (not editable) — the latter inside `runner.Run` rolls back the whole generation; refusal fallback back to the Revit number can steal a later group's Kata target (do two passes). `KataSupportTopBarLayout.Spread` at a width-changing support: odd counts (`3f20;3f16`) put both middle bars at y 0 overlapping ~450 mm. Inner U 4Ø/5.5Ø returns likely too short for Revit bends (CHƯA TEST). Left cantilever + row-20 cells throws in KataWidthProfile/KataAnchorage (pre-existing).
**Why:** golden tests (DY7: 3 spans, Ø18, symmetric cells, no cantilever) cover none of these.
**How to apply:** probe with a scratch console (`ProjectReference` to HPRebar.Core.csproj, copy `KataDy7DrawingTests.Sheet()` body, `KataCellTable` lives in Core) and mutate cells (`E14 = "2f20;2f18"`, `J7 = "a5"`, `I11 = 0` for a right cantilever). Run `dotnet test` from `HPRebar/` or the test folder (see [[project-dotnet-test-zero-tests-from-repo-root]]). BarId has no consumer outside tests — renumbering is safe.
